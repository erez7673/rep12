# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Rep12 (formerly Fressi Workout): a workout PWA. The site and the repo are reachable by anyone with the link (GitHub Pages, public repo) but not announced; the page has `noindex, nofollow` so search engines don't list it (remove the meta tag in `docs/index.html` when launching). It started as an app for a couple at Fressi Jätkäsaari gym, Helsinki; keep the UI free of gym and machine-brand names (gym80, Matrix). All pictures are our own (no maker pictures since 2026-11-23). The localStorage key stays `fressi.v1` so existing data survives. Plain HTML/CSS/ES-module JavaScript with **no build step, no package manager and no tests**. `SPEC.md` holds the original requirements; `README.md` holds the user-facing setup guide (GitHub Pages, phone install, Google Sheets sync).

- App source: `docs/` (GitHub Pages serves `main` branch, `/docs` folder) → https://erez7673.github.io/rep12/ (repo `erez7673/rep12`, formerly `fressi-workout`)
- Sync backend: `apps-script/Code.gs` (Google Apps Script web app over a Google Sheet)
- `Example App/` and `Fressi Gym equipment/` are reference photos only; they are git-ignored and must never be published.

## Commands

Run locally (also defined as `fressi` in `.claude/launch.json`, so use `preview_start` with that name):

```powershell
python tools/devserver.py 8765
```

`tools/devserver.py` is `http.server` with `Cache-Control: no-store` and no 304 answers, so a phone testing at `http://<PC address>:8765` always gets the newest files (the plain `python -m http.server` let the phone keep running old JS). The service worker registers only on https, so localhost always serves fresh files. If the browser still shows stale CSS/JS, re-fetch with `fetch(url, {cache: 'reload'})` and reload.

Deploy = commit and push to `main`; GitHub Pages is live about 30 s later. On phones, users get updates by closing and reopening the app (the service worker is network-first).

## Architecture

**Shell and routing (`app.js`).** A hash router (`ROUTES`) maps `#/plan`, `#/day/<week>/<day>`, `#/session`, `#/ex/<id>`, `#/gym`, `#/onboard[/edit]`, `#/custom`, etc. to view functions. Each view returns `{html, cls?, full?, after?}`; `render()` writes the html into `#view`. `rerender()` re-renders and keeps the scroll position. The bottom tab labels stay on one line (a second line pushes the icon out of the bar): `fitNav()` shrinks a label that is too wide, down to 8.5 px, but keep tab-name translations short (about 10 characters). A 250 ms interval drives all timers by updating elements marked `data-t="elapsed|rest|work|restbar|cardio|live"` in place, without re-rendering.

**Events go through an action registry (`ui.js`).** Markup never contains inline handlers. Use `data-act="name"` for clicks, `data-change="name"` for change events and `data-input="name"` for input events, then `register({ name: (el, e) => … })` in the view module. Pass parameters as `data-*` attributes. Bottom sheets are opened with `sheet(html)` and closed with the `sheet-close` action. Swipe-down to close does not work, so give a sheet a close X in the top-right corner (`closeX` in `views-plan.js`, class `sheet-x`, sticky while the sheet scrolls).

**State (`store.js`).** There is a single `state` object, persisted to localStorage key `fressi.v1`. It holds `profiles` (each with `stats`, `plan`, `history`, `bodyweight`), `gym` (equipment toggles, photographed machines, custom exercises), `settings` and the live `session`. After changing anything:
- mutate the object;
- call `touchProfile(p)` or `touchGym()` to bump `updatedAt` and save;
- call `scheduleSync()`.

**Sync (`sync.js` ↔ `Code.gs`).** Records are keyed `gym` and `profile:<id>`. The newest `updatedAt` wins per record (pull, then push). Requests are `text/plain` POSTs, which avoids a CORS preflight. `settings` and `session` are never synced. Both phones run the same code, so any data migration must be deterministic.

**Data model of exercises (`exercises.js`, `equipment.js`).** An exercise's `eq` string expresses equipment requirements: `a+b` means both are needed, `x|y` means alternatives, and `none` means bodyweight. `isAvailable()` / `eqOn()` in `store.js` evaluate it against Gym Setup. Exercises also carry the following fields, which drive the planner and the "What is this machine?" picker (`identify.js`):
- `pat`: plan slot pattern;
- `m` / `s`: primary and secondary muscles;
- `avoid`: injuries;
- `load`: starting weight as a fraction of body weight;
- `unit`: `reps`, `sec` or `min`;
- `pos`, `grip`, `mot`: used only by the picker.

**Planner (`planner.js`).**
- `generatePlan` builds a 12-week plan: a split chosen by days per week (`SPLITS`, 2–`MAX_DAYS` = 7; 6 = Push/Pull/Legs ×2, 7 adds a full-body day), `exPerDay(stats)` exercises (the profile's choice, 1–`MAX_EX_PER_DAY` = 8, default `EX_PER_DAY` = 4) × `SETS = 4` sets, plus warm-up, an optional cardio finisher and a cooldown. With many exercises the session length can't be met: `restScale` bottoms out and the day view shows the real (longer) time.
- **Muscle areas per day.** `AREAS` (legs, glutes, back, chest, …) map to slot patterns. Profile → Build your custom plan stores the areas for each day in `p.stats.dayAreas`; `areasFor(p, dayIdx)` reads them, `setDayAreas` rebuilds one day, and `applyProfileAreas(p)` reconciles all days at startup and after a sync pull (seeded, so both phones get the same result). `sortDay` orders a day's exercises bigger muscles first (`AREA_ORDER`, compound before isolation); call it after any change to a day's exercise list. A day the user reordered with the move button (`move-open` sheet in `views-plan.js`) has `day.manual = true` and `sortDay` leaves it alone; `setDayAreas` and "Back to the app's order" clear it. "Add to workout" on a full day can add the exercise as an extra one: `raiseDayCap` raises `p.stats.exPerDay` (or `plan.cap` for an app-built plan, which `dayCap` reads), max 8; other days are not filled up. `itemsForAreas` takes one exercise from each area in turn and starts the area lists over when they run out (for up to 8 a day), stopping when nothing new fits. `itemArea` gives the area header shown in the day view, and `swapOptions` offers every suitable exercise of the same area.
- `restScale` shortens rests (minimum 45 s) so the longest day fits the session length.
- `prescribe` sets reps and rest by goal and phase: base, build (more reps), peak (heavier), and a deload in week 12. **Custom plans have no phases** (the user's decision): a plan saved from "Build your custom plan" gets `plan.custom = true` and keeps the base sets and reps all 12 weeks, with no deload; `isCustom()`/`planPhase()` decide. Plans from onboarding, Edit profile → rebuild and app-built plans step up through the phases; Gym → Rebuild keeps the flag.
- `suggest` does progressive overload from the last log. When an exercise has no log yet, it uses `p.startKg[exId]`, falling back to a body-weight estimate.
- `buildSession` turns a plan day into session items and applies the user's pre-session edits from `p.plan.edits["<week>-<day>-<exId>"]`.
- **App-built plans (`TEMPLATES`, `generateTemplatePlan`).** Called "App-built plans" in the UI (formerly "Ready-made plans"; the user wants no "beginner" or "50+" wording). Stored as a normal plan with `plan.template`; `dayCap(p)` (not `exPerDay`) is the per-day exercise limit. Picked from the `tpl-open` sheet (My Plan → plan info, Profile). Two kinds:
  - Full-body plans (`starter`, `steady`, `short`): fixed slots in `TPL_DAYS`, each listing preferred exercise ids with a fallback to `candidates()` when equipment is off or an injury applies; gentle sets via `TPL_RX` (2–3 sets of 10–15 reps). `seated` (Seated, 3 days, `seated: true`) works the same way but uses only exercises done sitting on a machine or bench or lying on a bench (`isSeatedEx`: `pos` seated/incline/lying, minus the floor moves in `FLOOR`), for wheelchair users and people with balance or leg limitations; its fallbacks, cardio (bikes only) and `swapOptions` keep to seated exercises.
  - Split plans with `areas` per day and `goalRx: true`: `ab` (AB Plan, 4 days: A = chest, biceps, back; B = shoulders, triceps, legs) and `upperlower` (4 days: chest, back, shoulders, biceps, triceps / legs, glutes, calves, core). Days are filled with `itemsForAreas`, sets and reps follow the profile's goal (`tplRx(plan)` returns null for them, so `prescribe` uses the goal), and rests are shortened like `generatePlan`. Choosing one clears `p.stats.dayAreas`, since the plan brings its own areas.
- **Plan format is versioned (`PLAN_FMT`).** When the plan shape changes, bump `PLAN_FMT` and extend `upgradePlan`. `app.js` runs `upgradePlan` on every profile at startup and again after a sync pull. It must keep `id`, `createdAt` and finished weeks (`done`).

**Workout runtime (`workout.js`).** Holds the session state machine: set and rest timers stored as timestamps (so they survive a locked screen), beeps through Web Audio (no vibration, by design) and the screen wake lock.

**Views.**
- `views-plan.js`: plan, day preview with the set editor, session, summary. In the day preview the warm-up machine (`warm-open`, profile-wide `p.warm`) and the cardio finisher (`cardio-open`, per day: `plan.days[d].cardio = {exId, min}`, all weeks; `min: 0` = left out, `buildSession` skips it) each have a Change sheet; both also update an open workout whose timer hasn't started. The mobility routine is a button that opens the moves in a sheet (`mobility-open`).
- `views-gym.js`: exercise library, exercise page, Gym Setup, identify.
- `views-me.js`: profile forms, profile, **Settings** (`#/settings`, the gear at the top of Profile: language, units, appearance, rest beep, Google Sheets sync, backup, About with the privacy note and health disclaimer; the welcome screen shows the disclaimer too), progress (charts in `charts.js`). `profileForm(mode)` builds three forms: `new` (onboarding: everything except muscle areas), `edit` (`#/onboard/edit`: name to training days per week) and `custom` (`#/custom`, "Build your custom plan": exercises per day, muscle areas per day, session length, warm-up, cardio, injuries, extra focus). `readForm` only reads the fields present, so each screen changes only its own part of `p.stats`.
- **Accessibility (`#/access`, `accessView` in `views-me.js`).** Opened from the person icon at the top of Profile (`.a11y-btn`, next to the gear), on the welcome screen, and from Settings. Settings are per phone (`state.settings`, not synced):
  - `textSize` (`normal`, `large`, `xl`);
  - `contrast`;
  - `bigButtons`;
  - `speak`.

  `applyA11y()` in `ui.js` (and the inline script in `index.html`, before the first paint) writes them to `<html data-text|data-contrast|data-big>`. Effects:
  - **Text size:** every `font-size` in `app.css` is `calc(Npx * var(--fs))`, so write new font sizes the same way.
  - **High contrast** redefines the colour tokens.
  - **Bigger buttons** raises the tap sizes.
  - **Spoken cues** (`speak.js`, the phone's text-to-speech in the app's language):
    - "Set done, rest N seconds, next: …" when a set is logged;
    - "10 seconds left" (rests over 20 s, the `rest-10` event from `W.tick()`);
    - "Rest over, <exercise>, set a of b" when rest ends;
    - hold done, warm-up and cardio done, and the Timer countdown.

  Screen readers:
  - Every icon-only button or link needs an `aria-label` (icons are `aria-hidden`), and every input needs a label.
  - A clickable non-button gets `role="button" tabindex="0"`.
  - Sheets are `role="dialog"` and take focus, then give it back when closed.
- `tour.js`: the app tour. `STEPS` lists each step (`sec` section, `route`, `sel` = part to highlight, `fixed` for parts that don't scroll); the overlay `#tour` dims the page, highlights the part and shows a card (white on light blue in light mode, blue on white in dark mode, the user's choice) with Previous, "Skip to <next section>", Next and a close X. It starts once after the first profile is made (`state.settings.tourDone`, not synced) and from Profile → Take the app tour. Order: Profile → Settings → My Plan → Workout day → Exercises → Gym → Timer → Progress. Its texts are translated like the rest of the app. The highlight is clipped where the card begins, so a tall part or a long translation never ends up under the card. **Every change to the app must update the tour in the same commit** (the user's rule): new features get a step, moved or removed items get their step changed, and every `sel` must still match.
- `views-timer.js`: the stand-alone Timer tab (`#/timer`): countdown and stopwatch kept in `state.timer` as timestamps (not synced). `timerTick()` runs from the app's 250 ms loop and updates `data-t="tsw|tcd"`.

**Language and units (`i18n.js`, `localize.js`, `lang/`).**
- **Every text the user sees goes through `t('English text', {vars})`** (in `views-timer.js` and `identify.js` it is imported as `tr`, because `t` is a local variable there). Write the English text inline; use `{name}` placeholders, never string concatenation, and keep the first argument a plain single-quoted string so the extractor finds it.
- 11 languages: en, es, pt (Brazilian), de, it, fi, sv, zh (Simplified), hi, ar, he. `READY` in `i18n.js` lists the ones offered in Settings. Arabic and Hebrew set `dir="rtl"`; CSS uses logical properties (`margin-inline-start`, `text-align: start`) plus `[dir="rtl"]` rules, and direction icons (`back`, `chev`) have `class="dir"` so they flip; arrow characters in text (›) go in `<i class="arw">›</i>` for the same reason.
- Translations: `docs/js/lang/keys.js` maps an id to each English text; `docs/js/lang/<code>.js` maps the same ids to the translation. Both are generated: edit the sources `tools/i18n/src/<code>.txt` and `<code>.b.txt` (`id<TAB>text` per line), then run `node tools/i18n/build.mjs` (checks missing ids and `{placeholders}`).
- **After adding or changing UI text:** run `node tools/i18n/extract.mjs` (adds new English texts to `keys.js` with new ids, never renumbers; writes what each language is missing to `tools/i18n/todo/<code>.json`, git-ignored), add the translations to every `src` file, then `node tools/i18n/build.mjs`. Until then the new text shows in English.
- Built-in data (exercise names, steps and tips, muscles, equipment, goals, areas, templates, warm-up and cooldown moves, picker answers) stays English in the source and is translated once at start-up by `localizeData()`; `walkData()` lists those fields for the extractor. Changing the language reloads the app. Stored names (plan and day names, history titles) are shown through `planTitle()`/`dayName()` so they follow the current language.
- Units: weights are always stored in kg and heights in cm. `state.settings.units` is `metric` or `us`; show weights with `fmtW`/`fmtKg` (number in the user's unit), read typed weights with `fromW`, and heights with `fmtH`/`toFtIn`. `wStep` turns an exercise's kg step into the nearest 2.5 lb step in US units, so suggestions land on 5 lb plates; `unitText` converts km/h and cm inside exercise texts. New users get their phone's language (if ready) and US units on a US phone; people who used the app before keep English and metric. Language and units are per phone (`settings`, not synced).

**Exercise animations (`anim.js`).** Shown under "How to do it" on the exercise page; `hasAnim(id)` decides whether the page shows an animation (written steps then go into a collapsed "Written steps" box).
- **Video clips (preferred):** ids listed in `VIDEOS` play `docs/media/anim/<id>-m.mp4` or `<id>-f.mp4` (poster `<id>-m|f.jpg`), chosen by the profile's `stats.sex`. The clips are AI-generated (Higgsfield) from our own grey mannequin stills with the worked muscles in orange, on a #1c1c1e background: 4 s, silent, 1:1, encoded to 480×480 H.264 (`-crf 23 -movflags +faststart`, about 125 KB each). Never use RepDB artwork as a reference: its license forbids it.
  - Workflow per exercise: a male still (`gpt_image_2_6`, the Leg Press male still as style reference; the male wears dark grey sports shorts), a female still edited from the male still (ponytail, grey sports top and shorts; making her from scratch can trip Higgsfield's safety filter), then a `seedance_2_0_mini` video per still (4 s, 480p, 1:1, no audio, start and end image = the still, static camera). Two-handed machines: say both arms move together, or the model may move one arm only. A barbell or Smith bar always runs across the body (perpendicular to it): when the plates face the camera, a bench exercise is shown from behind the head end looking down the body to the feet (the user's choice), and a standing exercise is shown from the front; side views have the bar end-on. For bench exercises the user wants a fairly low camera (about 30° above the bench, not top-down), placed behind the head end and swung about 35° to one side (a head-end three-quarter view), so the thighs are visible lying along the bench and the knees and feet are clearly at the far end. A low camera straight behind the head does NOT work: the chest hides the thighs, so the bent knees and feet seem to grow out of the shoulders (the user calls this "4 legs"). Make the still by editing an approved still ("move the camera …"), say "knees close together, nothing next to the shoulders or arms", and in the video prompt say the legs are completely frozen. **Leg check (every clip, not just the still):** look at a start frame and the bottom of the rep at full size; reject any frame where a knee, foot or leg appears beside the shoulders, arms or hips, legs spread sideways, or more than two legs are visible. When a new exercise shares a pose with an approved still (e.g. Smith bench vs barbell bench), edit the approved still and change only the equipment; generating from scratch can stretch the body. The video model sometimes adds a spotlight beam, so say "even soft studio light, no spotlight" in the prompt; ask for a "big, clearly visible range of motion" when a rep comes out too small; for one-arm cable moves use the person's own left/right and say which hand stays still. Check every clip's frames before using it. **Body-stretch rule (user requirement, from batch 6 on):** a still-to-same-still video lets the model drift the camera and lengthen the torso at the bottom of the rep. Instead make two stills, top and bottom of the rep, where the bottom still is a minimal edit of the top still ("only the bar and arms move; same camera, crop, machine, bench and body in exactly the same pixels"), and check them with a 50% overlay: only the moving limbs may show double. Generate the video with start image = top still and end image = bottom still (a half rep), then make the loop in ffmpeg: play at 2x speed, then reversed (`setpts=0.5*PTS`, `reverse`, `concat`), giving a 4 s rep that starts and ends on the top still. Before using a clip, overlay its middle and last frames on its first frame: the head, torso, hips, legs and equipment must line up; reject it if the body or machine shows double. **When the pose change is big** (hinges, deadlifts, lunges, step-ups), editing the top still re-frames the scene (it zooms, rotates or shrinks the body), so generate both keyframes in ONE 21:9 image instead ("two animation frames side by side, same locked-off camera, same zoom, same size", reference = the approved top still), split it into halves, then shift the bottom half sideways so the planted foot or the equipment lines up (template matching on the plain background: `tools/clips/align.py`; `tools/clips/align2.py` also fixes scale for edited stills). Make the female pair by editing the whole 21:9 male pair in one go; if a leg comes out stretched, edit the two male stills one at a time instead. Every video prompt must name the orange highlight ("glowing orange highlighted <muscles> … stay visible the whole time"), or the video model drops it.

**Service worker (`sw.js`).**
- App files are network-first and fall back to cache `rep12-vN`; pictures (`.jpg` under `/media/`: clip stills, product photos) are cache-first in `rep12-pics-vN`, so the lists show them offline; bump `PICS` when a picture is replaced.
- **When adding a JS/CSS file, add it to `FILES`**, otherwise it won't work offline.
- Bump `CACHE` when the set of files changes.
- Other files under `/media/` (the clips) bypass the service worker: iPhone Safari loads video with range requests, which the cache can't answer. Clips are therefore not available offline (their stills are) (beyond the browser's own HTTP cache).

## Conventions

- **UI text:** written in English through `t()` (see Language and units), plain wording aimed at non-technical users; weights and heights always through the unit helpers. The app is public: no gym names, no machine-brand names, nothing that assumes a couple or "both phones".
- **Theming:** light/dark is driven by CSS custom properties in `css/app.css`, switched by `data-theme` on `<html>` (auto follows the phone). Use existing tokens such as `--card`, `--ink`, `--ink3`, `--blue`, and don't invent new ones (e.g. there is no `--muted`).
- **Icons:** the UI uses line-icon SVGs from `icon` in `ui.js`, not emoji, for equipment and exercises.
- **Commits:** use a short imperative subject.
